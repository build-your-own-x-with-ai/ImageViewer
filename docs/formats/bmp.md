# BMP 格式剖析

对应代码：`lib/src/codecs/bmp/`，测试：`test/codecs/bmp_test.dart`

## 它的难点不在压缩，在版本繁多

大多数 BMP 根本没有压缩 —— 像素就那么直排着，理论上「读头部、读像素、
完事」。真正的工作量来自三十年里累积的兼容包袱：

* **六个 DIB 头版本**（12/40/52/56/108/124 字节），字段布局各不相同
* **七种位深**（1/2/4/8/16/24/32），前四种要查调色板
* **通道位置可由文件任意指定**（`BI_BITFIELDS`），不只有 RGB555/565
* **两套游程编码**（RLE4/RLE8），带转义命令与增量跳转
* **默认自底向上**存储

所以解码器的结构是「先把所有版本的花样归一化成一个 `BmpHeader`，再按位深
分派到三条像素读取路径」，而不是为每个版本各写一遍解码流程：

```
字节流 ─► BmpHeader.parse ─┬─► _decodeIndexed  (1/2/4/8 bpp，查调色板)
                           ├─► _decodeDirect   (16/24/32 bpp，掩码抽通道)
                           └─► _decodeRle      (RLE4/RLE8 → 索引 → 调色板)
```

## 文件结构

```
偏移  长度  内容
0     14    BITMAPFILEHEADER
14    N     DIB 头（长度 N 自描述，是版本的唯一判据）
14+N  ...   通道掩码（仅 40 字节头 + BI_BITFIELDS）或调色板
bfOffBits   像素数据
```

注意像素数据的位置由文件头里的 `bfOffBits` 指定，**不能**用
「14 + 头长 + 调色板长」推算 —— 现实中的文件常在调色板后留空隙。

### BITMAPFILEHEADER（14 字节）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | char[2] | bfType | 恒为 `'BM'`（0x42 0x4D） |
| 2 | u32 | bfSize | 声明的文件总长。**不可信，直接忽略** |
| 6 | u16 x2 | bfReserved | 保留，为 0 |
| 10 | u32 | bfOffBits | 像素数据的绝对偏移 |

### 六个 DIB 头版本

| 长度 | 名称 | 关键差异 |
|---|---|---|
| 12 | BITMAPCOREHEADER | OS/2 1.x。宽高是 **u16**，调色板项 **3 字节** |
| 40 | BITMAPINFOHEADER | Windows 3.0，绝大多数文件是这一版 |
| 52 | BITMAPV2INFOHEADER | 头部自带 RGB 三个掩码字段 |
| 56 | BITMAPV3INFOHEADER | 再加 alpha 掩码字段 |
| 108 | BITMAPV4HEADER | 加色彩空间类型、端点坐标、gamma |
| 124 | BITMAPV5HEADER | 加渲染意图与内嵌 ICC 配置文件 |

版本判据只有头部长度这一个数。这个设计的好处是老解码器遇到新文件也能工作
（多出来的字段跳过就是），代价是必须按长度分派，不能靠版本号。

BITMAPINFOHEADER 的字段（V2 及以后在此基础上追加）：

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 14 | u32 | biSize | 头部自身长度 = 40 |
| 18 | i32 | biWidth | 宽度，必须为正 |
| 22 | i32 | biHeight | **负数表示自顶向下** |
| 26 | u16 | biPlanes | 恒为 1 |
| 28 | u16 | biBitCount | 每像素位数 |
| 30 | u32 | biCompression | 压缩方式，见下表 |
| 34 | u32 | biSizeImage | 像素数据长度，可能为 0 或撒谎 |
| 38 | i32 | biXPelsPerMeter | 水平分辨率（像素/米） |
| 42 | i32 | biYPelsPerMeter | 垂直分辨率 |
| 46 | u32 | biClrUsed | 调色板项数，0 表示按位深取满表 |
| 50 | u32 | biClrImportant | 「重要颜色数」，历史遗留，忽略 |

### 压缩方式

| 代码 | 名称 | 本项目 |
|---|---|---|
| 0 | BI_RGB | 无压缩，支持 |
| 1 | BI_RLE8 | 8bpp 游程，支持 |
| 2 | BI_RLE4 | 4bpp 游程，支持 |
| 3 | BI_BITFIELDS | 无压缩 + 自定义掩码，支持 |
| 4 | BI_JPEG | 像素数据是整个 JPEG 文件，**明确拒绝** |
| 5 | BI_PNG | 像素数据是整个 PNG 文件，**明确拒绝** |
| 6 | BI_ALPHABITFIELDS | 同 3 但含 alpha 掩码，支持 |

代码 4/5 在规范里有，现实中几乎只出现在打印驱动的私有用法里。与其悄悄解错，
不如抛 `UnsupportedImageFeature` 说清楚。

## 三个经典 bug

这三个是写 BMP 解码器几乎人人都会踩一遍的坑，测试里各有专门用例守着。

### 1. 每行按 4 字节对齐

**每一行的字节数都向上取整到 4 的倍数**，行尾补填充字节。公式：

```dart
int get rowStride => ((width * bitsPerPixel + 31) ~/ 32) * 4;
```

`+31 ~/ 32` 是「向上取整到 32 位」的惯用写法，再乘 4 换成字节数。

宽 3 的 24bpp 图，一行像素是 9 字节，但实际占 **12** 字节。用 `width * 3`
当行距，第一行看着是对的，第二行开始整片错位 —— 症状是图像斜着扭曲。

| 位深 | 宽 | 像素字节 | 实际行距 |
|---|---|---|---|
| 24 | 3 | 9 | 12 |
| 24 | 4 | 12 | 12 |
| 16 | 3 | 6 | 8 |
| 8 | 5 | 5 | 8 |
| 4 | 3 | 2 | 4 |
| 1 | 33 | 5 | 8 |

填充字节的内容未定义，读到它就说明算错了 —— 所以测试里故意把填充字节填 0，
错位时会解出黑色，一眼能看出来。

### 2. 默认自底向上

数据里的第一行是图像的**最后一行**。这源自 OS/2 的坐标系约定（原点在左下角）。
`biHeight` 为负时才是自顶向下，此时高度取绝对值。

```dart
int _outputRow(BmpHeader h, int storageRow) =>
    h.isTopDown ? storageRow : h.height - 1 - storageRow;
```

压缩与非压缩两条路都走这个函数，保证翻转逻辑只有一份。忘了翻转的症状很明显
（图像上下颠倒），但只对着方形纯色图测的话不会发现。

### 3. 低位深通道要按比例缩放，不能左移

RGB555 里红色占 5 位，最大值 31 必须映射到 **255**。左移 3 位只能得到 248 ——
白色会发灰。正确做法：

```dart
int extract(int pixel) {
  final int maxValue = (1 << width) - 1;
  final int v = (pixel >> shift) & maxValue;
  return (v * 255 + maxValue ~/ 2) ~/ maxValue;  // 四舍五入
}
```

| 位宽 | 原值 | 左移（错） | 比例缩放（对） |
|---|---|---|---|
| 5 | 31 | 248 | 255 |
| 5 | 16 | 128 | 132 |
| 6 | 63 | 252 | 255 |
| 4 | 15 | 240 | 255 |

8 位通道直接透传，不必走这个公式。

## 调色板（1 / 2 / 4 / 8 bpp）

位置在 DIB 头之后，每项字节数按版本不同：CORE 版是 3 字节 RGB 三元组，其余各版
是 4 字节 BGRA（第四字节通常为 0 且被忽略）。**顺序是 BGR，不是 RGB。**

项数取 `biClrUsed`，为 0 时按位深取满表（`2^bpp`）。但这个数来自文件，可能声明
一个荒谬的大值，所以要按 `1 << bpp` 硬上限截断，再按「调色板不能越过
`bfOffBits`」二次截断。

现实中存在「声明满表但只写了用到的几项」的文件，所以这里选择**截断而不报错**，
把问题推迟到解码时：像素里出现越界索引就填不透明黑并计数，计数出现在信息面板上
（`越界调色板索引`）。拒绝整个文件的代价太大，而这类文件用其他看图软件都能打开。

索引的位序是**高位在前**：1bpp 时 `x=0` 取字节的最高位。

```dart
final int byte = bytes[rowStart + x ~/ pixelsPerByte];
final int shift = 8 - bpp - (x % pixelsPerByte) * bpp;
final int index = (byte >> shift) & mask;
```

2bpp 不在原始规范里（Windows CE 用过），但解码逻辑与 1/4 完全同构，顺手支持。

## 通道掩码（16 / 32 bpp）

`BI_BITFIELDS` 让文件自己声明每个通道占哪几位。常见的是 RGB555、RGB565、
BGRA8888，但规范允许**任意**掩码 —— 见过 4-4-4-4 的，也见过通道顺序颠倒的。
所以不能为每种排列写分支，必须参数化：从掩码算出移位量（末尾零个数）与位宽
（1 的个数），再统一缩放。见 `ChannelMask`。

**掩码可能出现在两个不同位置**，这是 BMP 最容易搞错的细节：

* **V2 及以后**（头 >= 52 字节）：掩码是 DIB 头自身的字段
* **40 字节 INFO 头 + BI_BITFIELDS**：掩码放在**调色板区域**的前 12（或 16）字节

后一种是历史包裹 —— Windows 3.0 时代 INFO 头已经定型，要加掩码只能借用调色板的
位置。

不声明掩码时按位深取默认值：

| 位深 | 默认布局 |
|---|---|
| 16 | RGB555（`0x7C00` / `0x03E0` / `0x001F`），最高位不用 |
| 32 | BGRX（`0x00FF0000` / `0x0000FF00` / `0x000000FF`） |

RGB565 **必须**靠 `BI_BITFIELDS` 声明，不能靠猜。

### 32bpp 的 alpha 要靠启发式

规范说 32bpp `BI_RGB` 的第四字节是填充位。但实践中一半的文件在那里放了 alpha，
另一半留 0。两种都当真 alpha 用的话，后者会解成整张全透明图。

所以：掩码是**显式声明**的（`BI_BITFIELDS` / `BI_ALPHABITFIELDS` / V3+ 头）就直接
信任；是按位深**默认推出**的（标记 `alphaIsImplicit`）就扫一遍全图，全零按不透明
处理，有非零值才当 alpha 用。

## 游程编码（RLE4 / RLE8）

数据是一串两字节的命令对，第一字节决定如何解释第二字节：

```
(n, v)   n >= 1   编码游程：输出 n 个像素
(0, 0)             行结束，回到行首下移一行
(0, 1)             图像结束
(0, 2)   + dx, dy  增量跳转：当前位置移动 (dx, dy)
(0, n)   n >= 3    绝对模式：接下来 n 个像素是字面值
```

RLE4 与 RLE8 的实质差别只有一处：**RLE4 的编码游程在两个半字节间交替**。
`(5, 0x12)` 输出 `1 2 1 2 1`，不是五个 `0x12`。

### 两个容易漏掉的规则

**1. 绝对模式的数据要填充到偶数字节。**

RLE8 里 3 个像素占 3 字节，要补 1 个填充字节到 4；RLE4 里 5 个像素打包成 3 字节，
也要补到 4。漏掉填充会让后续**所有**命令错位。

| | 像素数 | 数据字节 | 含填充 |
|---|---|---|---|
| RLE8 | 3 | 3 | 4 |
| RLE8 | 4 | 4 | 4 |
| RLE4 | 5 | 3 | 4 |
| RLE4 | 4 | 2 | 2 |

**2. 未写到的像素保持索引 0。**

增量跳转会跳过一片区域，行结束时右边也可能有剩余。这些像素按规范是「未定义」，
实践中一律填 0（对应调色板第 0 项）。

畸形数据的处理策略：游程长度超出行宽就静默丢弃多余部分，数据提前耗尽就按已解出
的部分返回 —— 这两种在真实文件里都很常见。只有「绝对模式声明的字节数超出剩余
数据」和「增量跳转命令后缺 dx/dy」才报错，因为那说明数据确实断了。

`BmpRleDecoder.decode` 返回的是**存储顺序的调色板索引缓冲**，不是 RGBA。行方向的
翻转和索引到颜色的映射都留给主解码器，这样游程逻辑与调色板逻辑互不纠缠，翻转也
只有一份实现。

## 字节级实例

一张 2x2 的 24bpp BMP，共 70 字节。左上蓝、右上白、左下红、右下绿：

```
偏移  字节                                              含义
0000  42 4D                                            'BM'
0002  46 00 00 00                                      bfSize = 70（忽略）
0006  00 00 00 00                                      bfReserved
000A  36 00 00 00                                      bfOffBits = 54
                                                       —— DIB 头开始 ——
000E  28 00 00 00                                      biSize = 40
0012  02 00 00 00                                      biWidth = 2
0016  02 00 00 00                                      biHeight = 2（正 → 自底向上）
001A  01 00                                            biPlanes = 1
001C  18 00                                            biBitCount = 24
001E  00 00 00 00                                      biCompression = BI_RGB
0022  10 00 00 00                                      biSizeImage = 16
0026  00 00 00 00  00 00 00 00                         分辨率，未声明
002E  00 00 00 00  00 00 00 00                         biClrUsed / biClrImportant
                                                       —— 像素数据（偏移 54）——
0036  00 00 FF  00 FF 00  00 00                        存储行 0：红、绿 + 2 填充
003E  FF 00 00  FF FF FF  00 00                        存储行 1：蓝、白 + 2 填充
```

三处要一起看才对：

* 行距是 **8** 字节（6 字节像素 + 2 字节填充），不是 6
* 每像素是 **BGR** 顺序：`00 00 FF` 是红，不是蓝
* 存储行 1 是图像的**第一行**（自底向上）

所以最终图像是：

```
(0,0) 蓝  (1,0) 白
(0,1) 红  (1,1) 绿
```

## 不在范围内

* **内嵌 JPEG / PNG**（`BI_JPEG` / `BI_PNG`）—— 抛 `UnsupportedImageFeature`
* **OS/2 2.x 的 64 字节头** —— 极罕见，`BmpHeaderVersion.fromSize(64)` 会报错
* **ICC 色彩管理** —— V5 头里的配置文件字段被跳过，一律按 sRGB 显示
* **V4/V5 的 gamma 与端点坐标** —— 同上，读到但不参与计算
* **`biClrImportant`** —— 调色板优化的历史遗留，无视觉影响
