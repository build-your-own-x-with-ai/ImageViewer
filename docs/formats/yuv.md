# YUV 裸流剖析

对应代码：`lib/src/codecs/yuv/`，测试：`test/codecs/yuv_test.dart`

## 它跟另外五种格式根本不是一类东西

BMP、PNM、PNG、JPEG、WebP 都是**文件格式**：有魔数、有头部，打开就知道
自己是什么。YUV 不是格式，是**内存布局的约定**。一个 `.yuv` 文件里只有
采样值，没有任何自描述信息：

```
文件开头                                            文件结尾
├──────────────────────────────────────────────────────┤
 76 76 76 76 ... 85 85 ... 255 255 ...
 ↑ 这是什么？宽多少？I420 还是 NV12？BT.601 还是 BT.709？
   文件本身一个字都没说。
```

所以这个解码器的入口跟其他五个不一样 —— 它需要参数：

```dart
// 其他格式
decoder.decode(bytes);

// YUV：宽、高、像素格式、色彩矩阵、取值范围，五个都得给
decoder.decodeWith(bytes, YuvOptions(
  width: 1920, height: 1080,
  format: YuvFormat.i420,
  matrix: YuvMatrix.bt709,
  range: YuvRange.limited,
));
```

这也是 `canDecode` 永远返回 `false` 的原因。它没有魔数可查，如果返回
`true`，YUV 就会接管所有认不出来的文件，把「未知格式」变成一屏彩色噪点 ——
用户看到的不是错误提示，而是一张看起来「像图但不对」的图，更难排查。

## 为什么要有 YUV

RGB 三个通道地位平等，但人眼不平等：视网膜的亮度分辨率远高于色度。把
亮度（Y）和色度（U、V）分开存，就可以只压缩色度 —— 色度降到四分之一
分辨率，多数人看不出差别，数据量却直接掉一半。

这个思路是 JPEG、H.264、HEVC 全都在用的第一步。**所以 YUV 不只是「一种
格式」，它是理解 JPEG 和视频编码的前置知识**，这也是把它放在阶段 1 的原因。

### 抽样记号 J:a:b

| 记号 | 含义 | 色度尺寸 | 每像素字节 |
|---|---|---|---|
| 4:4:4 | 不抽样 | 与亮度同尺寸 | 3 |
| 4:2:2 | 水平减半 | `⌈w/2⌉ × h` | 2 |
| 4:2:0 | 水平垂直都减半 | `⌈w/2⌉ × ⌈h/2⌉` | 1.5 |

记号本身是历史包袱，不必深究：`J` 是参考块宽度（4），`a` 是第一行的色度
样本数，`b` 是第二行的。**只需记住 4:2:0 的「0」不是「垂直不采样」，而是
「第二行不额外采样、跟第一行共用」。**

## 三种平面布局

抽样比只决定**有多少个**色度样本，不决定它们**摆在哪**。同样是 4:2:0，
摆法就有三种，这是 YUV 里最容易混淆的地方。以 4×2 图像为例，12 字节：

```
planar（I420）      Y Y Y Y Y Y Y Y | U U | V V
                    └─ 8 字节 ─────┘ └2┘   └2┘
                    三个平面完全分开

semiPlanar（NV12）  Y Y Y Y Y Y Y Y | U V U V
                                      └─ 交织 ─┘
                    亮度一个平面，色度两通道交织成第二个平面

packed（YUY2）      Y U Y V Y U Y V | Y U Y V Y U Y V
                    └ 宏像素 ┘        （只有一个平面，且是 4:2:2）
                    亮度色度全交织，两个像素一组
```

**同样的 12 字节，按 I420 和按 NV12 解出来是不同的图。**这一点在
`test/codecs/yuv_test.dart` 的「I420 与 NV12 的区别是平面 vs 交织」
一例里被显式测了 —— 顺带说明为什么 2×2 测不出差别（2×2 时色度只有一个
样本，两种摆法恰好等价，所以测试必须用 4×2）。

## 九种格式

| 格式 | 布局 | 抽样 | U/V 顺序 | 别名 | 常见来源 |
|---|---|---|---|---|---|
| I420 | planar | 4:2:0 | U 先 | YU12 | ffmpeg 默认、多数编码器 |
| YV12 | planar | 4:2:0 | **V 先** | — | Android 早期、DirectShow |
| I422 | planar | 4:2:2 | U 先 | YUV422P | 专业视频 |
| I444 | planar | 4:4:4 | U 先 | YUV444P | 无抽样损失的中间格式 |
| NV12 | semiPlanar | 4:2:0 | U 先 | — | iOS 摄像头、硬件解码器 |
| NV21 | semiPlanar | 4:2:0 | **V 先** | — | Android 摄像头 |
| YUY2 | packed | 4:2:2 | U 先 | YUYV / V422 | 摄像头采集 |
| YVYU | packed | 4:2:2 | **V 先** | — | 少见 |
| UYVY | packed | 4:2:2 | U 先 | UYNV / Y422 | 采集卡、SDI |

注意表里的规律：**九种格式里有三对只差 U/V 顺序**（I420/YV12、
NV12/NV21、YUY2/YVYU）。这正是把布局参数化的理由 —— 代码里这三对
共用同一个循环，区别只是一个 `uFirst` 布尔值：

```dart
// planar：决定哪个平面在前
final int uPlane = start + w * h + (uFirst ? 0 : chromaSize);

// semiPlanar：决定交织时谁在偶字节
final int uOff = uFirst ? 0 : 1;
```

九种格式 → 三个循环，而不是九个。`YuvFormat` 这个枚举承担的就是这件事。

## 色彩转换：六个系数全部由 kr / kb 推出

网上到处能查到的那串魔法数字：

```
R = 1.164(Y-16)                + 1.596(V-128)
G = 1.164(Y-16) - 0.391(U-128) - 0.813(V-128)
B = 1.164(Y-16) + 2.017(U-128)
```

直接抄能用，但换成 BT.709 就得再抄一遍，换成 full range 又得抄一遍 ——
四种组合四套数字，抄错一个小数位，图能出来、颜色偏一点、肉眼极难发现。
所以代码里不抄，而是推。

### 正向定义

标准只规定两个数：`kr` 和 `kb`（红和蓝的亮度权重），`kg = 1 - kr - kb`。

```
Y  = kr·R + kg·G + kb·B
Cb = (B - Y) / (2(1-kb))        ← 除以 2(1-kb) 是为了把范围归一到 ±0.5
Cr = (R - Y) / (2(1-kr))
```

### 反解

前两行直接移项：

```
R = Y + 2(1-kr)·Cr
B = Y + 2(1-kb)·Cb
```

G 没有独立定义，得从 `Y = kr·R + kg·G + kb·B` 里挤出来：

```
kg·G = Y - kr·R - kb·B
     = Y - kr[Y + 2(1-kr)Cr] - kb[Y + 2(1-kb)Cb]
     = Y(1 - kr - kb) - kr·2(1-kr)·Cr - kb·2(1-kb)·Cb
     = kg·Y          - kr·2(1-kr)·Cr - kb·2(1-kb)·Cb

G = Y - [kb·2(1-kb)/kg]·Cb - [kr·2(1-kr)/kg]·Cr
       └──── gU ────────┘    └──── gV ────────┘
```

于是四个色度系数全部由 `kr`、`kb` 决定，代码里就是这四行：

```dart
rV = 2 * (1 - kr),                bU = 2 * (1 - kb),
gU = kb * 2 * (1 - kb) / kg,      gV = kr * 2 * (1 - kr) / kg,
```

### limited range 的两个拉伸比

广播视频不用满 0–255：**Y 占 16–235（219 级），U/V 占 16–240（224 级）**。
留出的余量叫 headroom / footroom，给滤波和转换的过冲留空间。所以解码时要
先拉回满量程，两个通道的拉伸比不一样：

```
亮度：255/219 ≈ 1.1644     ← 这就是那个 1.164 的来历
色度：255/224 ≈ 1.1384     ← 四个色度系数各乘这一个数
```

`YuvColorConverter` 里 `range` 只影响 `yScale`、`yOffset` 和这个色度乘数，
矩阵只影响 `kr`/`kb`。**三种矩阵 × 两种范围 = 六种组合，共用一条转换路径**，
没有一处硬编码的小数。测试里有一条结构性断言专门盯这件事：

```dart
// limited 的系数必须恰好是 full 的系数乘 255/224
expect(lim.rV, closeTo(full.rV * 255.0 / 224.0, 1e-12));
```

### 推导结果对照表

推完了还是要跟教科书对一遍 —— 这是 `yuv_test.dart` 里那组 `closeTo` 断言：

| 矩阵 / 范围 | Y 缩放 | R←V | G←U | G←V | B←U |
|---|---|---|---|---|---|
| BT.601 limited | 1.1644 | 1.5960 | 0.3918 | 0.8130 | 2.0172 |
| BT.601 full | 1.0000 | 1.4020 | 0.3441 | 0.7141 | 1.7720 |
| BT.709 limited | 1.1644 | 1.7927 | 0.2132 | 0.5329 | 2.1124 |
| BT.709 full | 1.0000 | 1.5748 | 0.1873 | 0.4681 | 1.8556 |
| BT.2020 full | 1.0000 | 1.4746 | 0.1646 | 0.5714 | 1.8814 |

第一行就是文章开头那串魔法数字。它不是魔法，是 `kr=0.299, kb=0.114`
配上 219/224 拉伸算出来的。

### 该用哪个矩阵

| 场景 | 矩阵 | 范围 |
|---|---|---|
| 标清视频、JPEG 内部 | BT.601 | JPEG 是 full，视频是 limited |
| 高清视频（720p 及以上） | BT.709 | limited |
| 4K / HDR | BT.2020 | limited |

猜错矩阵的后果是**颜色偏移但图形完全正常** —— 用 BT.601 解 1080p 的
BT.709 素材，肤色会偏，但你不会觉得「解码错了」。这是 YUV 最阴险的一类
问题，所以信息面板里把用的哪套系数原样列出来。

## 三个经典 bug

### 1. U/V 顺序：一个布尔值，红蓝互换

I420 和 YV12 的字节数、平面数、抽样比全都一样，**只有 U/V 两个平面的
先后顺序相反**。搞错了不会报错、不会崩，只会红蓝对调。

```
同样这 6 字节：128 128 128 128 | 255 | 128
                └── Y 2×2 ──┘   └A┘   └B┘

按 I420（U 先）：U=255 V=128 → cb=+127 cr=0  → 偏蓝  [128, 84, 255]
按 YV12（V 先）：V=255 U=128 → cr=+127 cb=0  → 偏红  [255, 37, 128]
```

Android 摄像头给 NV21、iOS 给 NV12，这一对同样只差 U/V 顺序 —— 跨平台
拿摄像头数据时，这是最常踩的坑。测试里这四个用例故意用**同一份字节**
喂给配对的两种格式，断言颜色互换，这才能证明 `uFirst` 真的在起作用，
而不是碰巧两边都读了同一个平面。

### 2. limited / full range：对比度不对，但看着「像是」正常

同一份字节，两种范围解出的灰阶不一样：

| Y 值 | full 解出 | limited 解出 |
|---|---|---|
| 0 | 0 | 0（夹住） |
| 16 | 16 | **0** |
| 126 | 126 | **128** |
| 235 | 235 | **255** |
| 255 | 255 | 255（夹住） |

把 limited 的素材当 full 解，黑不够黑、白不够白，整张图发灰；反过来则
对比度过强、暗部和高光被压平。两种情况都不会报错。

另外注意 limited 必须**夹取**而不是断言：广播信号里 Y 完全可以落在
16–235 之外（那就是 headroom 存在的意义），解码器遇到 Y=0 或 Y=255
要夹住输出，不能当成非法数据抛异常。

### 3. 尺寸猜错：不报错，解出一张斜纹图

这是 YUV 独有的、也是最费时间的一类问题。假设真实素材是 640×480 I420，
你按 638×480 去解：

```
每行少读 2 个字节 → 第二行的起点偏移 2 → 第三行偏移 4 → ...
结果：整张图向一侧倾斜，像被剪切变形过
```

**字节数够的时候，解码器没有任何办法发现这件事** —— 它拿到的就是一堆
数字，没有校验和、没有行分隔符。所以只能在字节数**不够**的时候把话说透。
`_describeMismatch` 会固定宽度和格式，反推出能让帧大小刚好对上的高度：

```
640x481 的 I420 每帧需 461760 字节，文件共 460800 字节：
按宽 640 与 I420 推算，这份数据的高度应是 480
```

反推不出整数高度时，退回来报还差多少字节。这个扫描只在报错路径上跑，
不影响正常解码。

## 奇数尺寸：色度平面向上取整

4:2:0 的色度尺寸是 `⌈w/2⌉ × ⌈h/2⌉`，**向上取整**。3 列亮度需要 2 列色度，
不是 1 列：

```
w=3:  Y0 Y1 Y2          h=3:  Y 行 0  ┐
      └─┬─┘ └┬┘               Y 行 1  ┴→ 色度行 0
        U0    U1               Y 行 2  ──→ 色度行 1
```

写成 `w ~/ 2` 会让 3×1 的 I422 只要 5 字节而不是 7，然后在最后一列
读到 V 平面的头上 —— 越界或者串色。取整方向写在 `chromaWidth` /
`chromaHeight` 两个方法里，测试里有专门的用例盯着 3×1 和 3×3。

索引时反过来用整除，这是**最近邻上采样**：

```dart
final int cx = x ~/ subX;      // 第 0、1 列共用色度第 0 列
final int cy = y ~/ subY;      // 第 0、1 行共用色度第 0 行
```

这里故意不做双线性插值。最近邻会让 4:2:0 的色块边界肉眼可见 —— 对教学
来说这是**特性不是缺陷**：能直接看出色度分辨率确实只有一半，抽样损失是
真实存在的。真实播放器会做插值，那是后续可以自己加的练习。

## 多帧：文件里可能不止一张图

`ffmpeg -i in.mp4 out.yuv` 导出的是**所有帧首尾相接**，没有任何分隔符：

```
[第 0 帧][第 1 帧][第 2 帧]...
 ↑ 每帧固定 frameSize 字节，所以第 N 帧的偏移 = frameSize × N
```

`YuvOptions.frameIndex` 就是为这个存在的。帧数由 `文件长度 ÷ 帧大小`
整除得出，残帧不计。

## 字节级实例

4×2 的 I420，左半红、右半绿，BT.601 full range，共 12 字节：

```
偏移  字节                        含义
────────────────────────────────────────────────────────
      ┌─ 亮度平面 4×2，逐像素 ─┐
00    4C 4C 96 96               Y 第 0 行：红 76, 76, 绿 150, 150
04    4C 4C 96 96               Y 第 1 行：同上
      ┌─ U 平面 2×1（4:2:0，宽高都减半）─┐
08    55 2C                     U：红块 85，绿块 44
      ┌─ V 平面 2×1 ─┐
0A    FF 15                     V：红块 255，绿块 21
```

解第 (0,0) 个像素，`cb = 85-128 = -43`，`cr = 255-128 = +127`：

```
R = 76 + 1.402·(+127)      = 76 + 178.1 = 254.1 → 254
G = 76 - 0.344·(-43) - 0.714·(+127) = 76 + 14.8 - 90.7 = 0.1 → 0
B = 76 + 1.772·(-43)       = 76 - 76.2  = -0.2  → 0（夹住）
                                                   └ 夹取是必须的
```

得到 `(254, 0, 0)` —— **不是 `(255, 0, 0)`**。绿块同理，`cb = 44-128 = -84`：

```
R = 150 - 0.344·(-84) - ... = 0（夹住）
G = 150 + ...              = 255（夹住）
B = 150 + 1.772·(-84)      = 150 - 148.8 = 1.15 → 1   ← 不是 0
```

两个块都回不到原始的纯色。**RGB → YUV → RGB 不是恒等变换**，哪怕用
I444 完全不抽样也一样：系数是无理数、中间量化到 8 bit，误差躲不掉。
所以元数据里 I444 标 `isLossless: true` 说的是「**没有抽样损失**」，
不是「往返无误差」—— 这是两件不同的事。

再看夹取：纯红的 Cr 算出来正好是 255，已经贴着上界；解回来 B 落在 -0.2，
纯绿的 R 落在负数、G 超过 255。**夹取不是防御性代码，是数学上必然发生的
情况** —— YUV 立方体比 RGB 立方体大，合法的 YUV 组合完全可以落在 RGB
色域之外（`yuv_test.dart` 里 `Y=235, U=V=16` 那个用例算出 G≈390）。

同样这 12 字节按 **NV12** 解会怎样？色度部分 `55 2C FF 15` 变成交织的
两组 `(U,V) = (85,44)` 和 `(255,21)`，第一个像素的 `cr` 从 +127 变成 -84，
解出来是绿而不是红。**一个参数选错，整张图的颜色全变。**

## 不在范围内

* **10/12/16 bit YUV**（P010、YUV420P10LE 等）—— HDR 素材常用，但要处理
  字节序和位移，跟本文的 8 bit 逻辑是两套代码
* **平面 stride ≠ 宽度** —— 硬件解码器输出常按 16/32 字节对齐，需要额外的
  stride 参数；本项目假设紧密排布
* **图块格式**（NV12T 等 GPU 平铺布局）—— 与具体硬件绑定
* **双线性 / Catmull-Rom 色度上采样** —— 见上文，故意留作练习
* **完整 range 的转换矩阵**（BT.470、SMPTE 240M 等历史矩阵）—— 加一个
  枚举项就能支持，只是现实中已很少遇到
