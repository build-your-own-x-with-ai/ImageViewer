# PNG 格式剖析

对应代码：`lib/src/codecs/png/` 与 `lib/src/compress/`，
测试：`test/codecs/png_test.dart`、`test/compress/`

## 它的难点全在压缩

BMP 的工作量来自三十年的版本包袱（六个头部版本、七种位深、两套 RLE）。
PNG 反过来：**格式本身 1996 年定型后几乎没变过**，字段少、规则干净、
顺序要求明确。难的是它把压缩这件事整个吞了进来。

要解一张 PNG，得先写一个完整的 deflate 解压器：三种块类型、规范化
Huffman 码表、码表自身还是 Huffman 编码的、LZ77 反向引用、两张写死在
规范里的长度/距离表。这部分在 `lib/src/compress/` 下 1069 行，比 PNG
解码器本体（1766 行里真正处理 PNG 语义的部分）更难写。

它放在 `compress/` 而不是 `codecs/png/` 下是有原因的：**WebP 的 VP8L 与
ALPH 会用到同一套 Huffman 机制**，阶段 4 要复用。依赖方向
`codecs → compress → core`，见 `design.md` §2。

于是这一份文档实际上讲两个东西：

```
文件字节
  ├─ chunk 层        签名、长度+类型+数据+CRC32        png_chunk.dart
  ├─ IHDR            宽高、位深、色彩类型、隔行         png_header.dart
  ├─ zlib + deflate  ← 全部工作量在这里              compress/*.dart
  ├─ 反滤波          五种滤波器逐行还原               png_filters.dart
  └─ 展开            采样 → RGBA8888                  png_pixels.dart
```

好处是每一层之间只用字节数组通信，没有跨层状态 —— 每一层都能单独测试。
这是 PNG 比 JPEG 好写得多的根本原因。

## 文件结构

```
偏移  长度  内容
0     8     签名 89 50 4E 47 0D 0A 1A 0A
8     ...   一串 chunk，第一个必须是 IHDR，最后一个必须是 IEND
```

没有别的了。所有信息都在 chunk 里，包括宽高。

### 签名的八个字节各在防一种传输事故

这是所有格式里设计得最讲究的魔数。1996 年的设计者假定文件会经过各种会
自作聪明改内容的通道（FTP 的文本模式、邮件网关）：

| 字节 | 值 | 防什么 |
|---|---|---|
| 0 | `0x89` | 高位为 1。走 7 位通道会被剥成 `0x09`，一测就知道 |
| 1–3 | `'PNG'` | 人能读出来，文本编辑器打开也认得 |
| 4–5 | `0x0D 0x0A` | CRLF。被转成单个 LF 就说明通道改过行尾 |
| 6 | `0x1A` | DOS 的 EOF。`TYPE 文件.png` 会停在这里，不刷屏乱码 |
| 7 | `0x0A` | LF。被转成 CRLF 同样能测出来 |

第 4–5 与第 7 字节合起来能识别**四种**行尾转换事故（CRLF→LF、LF→CRLF、
CR→CRLF、CRLF→CR）。放在今天多半是过度设计，但它是「魔数不只是标识，
还可以是探针」的最佳教材。

### chunk：自描述换来的向前兼容

```
长度(4, 大端)  类型(4, ASCII)  数据(长度字节)  CRC-32(4)
```

BMP 加字段就得加一个头部版本。PNG 避开了这条路：每块数据自带长度和类型，
解码器**遇到不认识的类型就按长度跳过**。于是三十年来 PNG 加了几十种
chunk（动画的 `acTL`、色彩管理的 `iCCP`、EXIF 的 `eXIf`），老解码器一个
都不认识却都能正常打开新文件。

代价是每个 chunk 12 字节固定开销。一张 2×2 的图有 82 字节，其中 36 字节
是三个 chunk 的开销 —— 小图上这个比例很难看，但它换来的是格式三十年没有
破坏性变更。

长度字段上限是 `2^31 - 1` 而不是 `2^32 - 1`，为的是让「int 是有符号
32 位」的语言也能安全处理而不出现负数。

### 类型名的大小写是四个功能位

四个字母各自的**第 5 位**（即大小写）都有含义：

| 字母 | 大写 | 小写 |
|---|---|---|
| 第 1 | 关键 chunk，不认识必须报错 | 辅助 chunk，可以跳过 |
| 第 2 | 公有（登记在册） | 私有扩展 |
| 第 3 | 保留，必须大写 | —— |
| 第 4 | 不可安全复制 | 编辑器改图后可以保留 |

于是解码器面对未知 chunk 时**不需要查表**就知道该报错还是该跳过 ——
判断依据就在名字里。`IHDR` 全大写：关键、公有、不可复制。`tEXt` 首字母
小写：辅助信息，跳过无妨。

本项目认识 8 种 chunk（`IHDR` / `PLTE` / `IDAT` / `IEND` / `tRNS` /
`gAMA` / `pHYs` / `tEXt`），其余按这四个位处理：未知关键 chunk 抛
`UnsupportedImageFeature`，未知辅助 chunk 只在信息面板里记一笔类型名。

### 一个文件里两套校验和，保护对象不同

初学者常以为其中一个多余：

| | 算法 | 保护对象 | 谁定的 |
|---|---|---|---|
| chunk 尾部 | CRC-32 | 该 chunk 的**类型 + 数据** | PNG 规范 |
| zlib 流尾部 | Adler-32 | **解压后**的原始字节 | RFC 1950 |

CRC-32 保证「压缩数据在传输中没坏」，Adler-32 保证「解压出来的东西和
压缩前一致」。前者验证密封的箱子，后者验证箱子里的货。

**一个解压器实现有 bug 时，CRC 会全部通过而 Adler 会报错。** 对自写
inflate 的项目来说，Adler-32 是最有价值的一道防线 —— 它是唯一能发现
「Huffman 解码错了但字节数恰好对上」这类错误的机制。

CRC 的计算范围**不含长度字段**，这是最容易写错的一处。长度被刻意排除
在外，于是解码器可以在不知道长度可信与否的情况下先读类型，再用 CRC
反过来确认长度也是对的。

生成多项式写作 `0xEDB88320`，是规范文档里 `0x04C11DB7` 的**位反转**
形式 —— 因为 CRC-32 按低位在前处理数据，反转过来写就能直接用右移实现。
两个常数看起来毫无关系，其实是同一个多项式。

## IHDR：13 个字节决定后面的一切

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u32 | 宽度 | 必须 > 0 |
| 4 | u32 | 高度 | 必须 > 0 |
| 8 | u8 | 位深 | 每**采样**的位数，不是每像素 |
| 9 | u8 | 色彩类型 | 0/2/3/4/6，见下 |
| 10 | u8 | 压缩方法 | 只允许 0（deflate） |
| 11 | u8 | 滤波方法 | 只允许 0（五种基础滤波器） |
| 12 | u8 | 隔行方式 | 0=无，1=Adam7 |

「位深是每采样而不是每像素」这一点值得强调：RGB8 的位深是 **8**，不是
24。一张 16 位 RGBA 图的位深是 16，每像素占 64 位。

第 10、11 两个字节三十年来始终只允许填 0 —— 预留的扩展位从没用上。但
留着不亏：两个字节换两条「以后可以换算法」的退路。

### 色彩类型编号跳着走，因为它是位标志

```
bit 0 (值 1) = 使用调色板
bit 1 (值 2) = 彩色（否则灰度）
bit 2 (值 4) = 带 alpha 通道
```

于是 2 = 彩色，3 = 彩色+调色板，4 = 灰度+alpha，6 = 彩色+alpha。
**1 和 5 从未被定义过** —— 调色板本身就隐含彩色（所以 1 是多余的），
而调色板的透明度走 `tRNS` 而不是第四通道（所以 5 用不着）。

看懂这一点，「为什么没有色彩类型 1 和 5」就不再是需要死记的事。

### 合法组合只有 15 种

位深合法（1/2/4/8/16）不够 —— 组合才是规范约束的对象：

| 类型 | 名称 | 通道 | 允许的位深 |
|---|---|---|---|
| 0 | 灰度 | 1 | 1, 2, 4, 8, 16 |
| 2 | 真彩色 RGB | 3 | 8, 16 |
| 3 | 调色板 | 1 | 1, 2, 4, 8 |
| 4 | 灰度 + alpha | 2 | 8, 16 |
| 6 | 真彩色 RGBA | 4 | 8, 16 |

约束都有实际理由：1 位真彩色说不通（三个通道各 1 位？）；16 位调色板
也说不通（调色板最多 256 项，索引最多 8 位）。

调色板类型的位深指的是**索引的位数**，不是颜色的位数 —— 调色板项恒为
8 位/通道。所以 `bitDepth: 4` 的调色板图有 16 种颜色，每种都是 24 位色。

### 由 IHDR 推导出来的四个量

后面每一步都靠这几个数，算错一个整张图就斜着错开：

```dart
int get bitsPerPixel => colorType.channels * bitDepth;
int get bytesPerPixel => bitsPerPixel < 8 ? 1 : bitsPerPixel ~/ 8;
int get bytesPerRow => (width * bitsPerPixel + 7) ~/ 8;   // 向上取整
int get rawSize => height * (bytesPerRow + 1);            // +1 是 filter 字节
```

`bytesPerPixel` 在位深小于 8 时**向上取整到 1**。滤波器做的是「当前字节
减去左边那个字节」，但 1 位灰度图一个字节里装了 8 个像素，「左边一个
像素」根本不在另一个字节里。规范的处理很干脆：位深小于 8 时 bpp 按 1
字节算。这在语义上有点糙（相当于减去左边 8 个像素中最远的那个），但
保持了「滤波器只跟字节打交道，完全不用理解像素格式」这个简洁性。

每行都单独向上取整到字节边界，**行与行之间不共享字节**。1 位深、宽 5
的图一行占 1 字节，末尾 3 位是填充。这一点和 BMP 的 4 字节行对齐是同类
问题，只是粒度不同：PNG 补到字节，BMP 补到 4 字节。

## deflate：真正的工作量

PNG 的像素数据外面套一层 zlib（RFC 1950），里面是 deflate（RFC 1951）。

### zlib 容器：两字节头 + 四字节尾

```
CMF  高 4 位 CINFO（窗口大小 = 2^(CINFO+8)），低 4 位 CM（压缩方法，只允许 8）
FLG  高 2 位压缩级别，bit 5 是 FDICT（预设字典，PNG 里禁止），低 5 位校验
     约束：(CMF * 256 + FLG) % 31 == 0
...  deflate 数据
尾   Adler-32，大端，覆盖解压后的字节
```

`% 31 == 0` 这个约束的作用是让「头部被改动」能被立刻发现 —— 两个字节的
组合里只有 1/31 是合法的。最常见的头是 `78 01`（CINFO=7 即 32KB 窗口、
CM=8、级别 0）。

### 三种块类型

每块开头是 3 位：1 位 BFINAL（是否最后一块）+ 2 位 BTYPE。

| BTYPE | 名称 | 什么时候用 |
|---|---|---|
| 00 | stored | 数据压不动（已压缩的、随机的），原样存反而更省 |
| 01 | 固定 Huffman | 码表写死在规范里，省掉传码表的开销，适合小数据 |
| 10 | 动态 Huffman | 按本块数据统计出码表，再连码表一起传 |
| 11 | —— | 保留，出现即报错 |

一个流里可以混用，压缩器逐块自行选择。stored 块要先跳到字节边界，然后
是 `LEN`（小端 u16）与 `NLEN`（LEN 的按位取反）—— 后者是冗余校验，
两者不互补就说明数据坏了。

### 规范化 Huffman：码长决定码字

看动态块时最大的困惑是：**码表里只有码长，码字呢？**

答案是码字可以由码长唯一推出来，只要双方约定同一条规则：

1. 按码长从小到大排；
2. 同码长内按符号编号从小到大排；
3. 第一个码字为 0，同码长内每个码字比前一个大 1；
4. 码长每增加 1，码字左移一位。

举例，四个符号 A/B/C/D 的码长分别是 2/1/3/3：

```
码长 1：B → 0
码长 2：A → 10          (0 + 1 = 1，左移 → 10)
码长 3：C → 110         (10 + 1 = 11，左移 → 110)
        D → 111
```

于是码流里只传 `[2, 1, 3, 3]` 就够了。这就是「规范化」的全部含义 ——
用一条排序约定换掉码字表本身。

**解码不需要建树。** 上面的规则意味着同码长的码字是连续递增的整数，
所以只要知道「每个码长有几个码字」和「该码长的首码字」，就能靠一次减法
算出符号在表里的下标。数据结构因此退化成两个平坦数组，解码循环二十行、
无指针跳转、无内存分配。

建表时顺带做完整性校验（Kraft 不等式 `Σ 2^-len`）：

* **过订阅**（`> 1`）：某码长的码字个数超过该长度能容纳的数量，比如声明
  三个 1 位码字。一定是数据损坏，拒绝。
* **不完整**（`< 1`）：码字没用满编码空间，存在没有符号对应的位模式。
  **符号数 ≤ 1 时放行，否则拒绝** —— 「只有一个符号」是真实存在的正常
  情况（全图只有一种距离时距离表就只有一个 1 位码字），zlib 也这么处理。

这是**唯一**能廉价发现码表损坏的时机。一旦进了解码循环，错误只会表现为
「解出一堆合法但错误的字节」。

### 动态块：码表本身也是 Huffman 编码的

这是 deflate 最绕的一层。块头之后：

```
HLIT   5 位，字面/长度码的个数 - 257
HDIST  5 位，距离码的个数 - 1
HCLEN  4 位，码长码的个数 - 4
```

接着是 `HCLEN + 4` 个 3 位值，它们是**码长字母表**的码长。而这些值不按
0..18 的自然顺序传，按这个顺序：

```
16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15
```

顺序是按「出现概率从高到低」排的 —— 常用的码长（8 附近）排在前面，
于是 HCLEN 往往能砍掉尾部一截不传。这是一个纯粹的空间优化。

用这张码长表解出的 Huffman 码表，再去解字面/长度码表与距离码表的码长
序列。这一层里有三个特殊符号：

| 符号 | 含义 |
|---|---|
| 16 | 重复**上一个**码长，额外 2 位（3–6 次） |
| 17 | 重复码长 0，额外 3 位（3–10 次） |
| 18 | 重复码长 0，额外 7 位（11–138 次） |

17/18 分开是因为「一长串未使用的符号」极常见（288 个字面符号里往往只用
一小半），给它一个 7 位额外位的专用符号很划算。

符号 16 有个陷阱：它重复的是「上一个码长」，而这个「上一个」可能跨越
字面表与距离表的边界 —— 两张表的码长序列是**连成一串**传的，不是各传
一段。按两段分开读就会在边界上错。

### LZ77 反向引用

字面/长度字母表里，0..255 是字面量，256 是块结束符，257..285 是长度码。
读到长度码后再读一个距离码，得到「往回 D 字节，复制 L 字节」。

两张表都写死在规范里（`deflate_tables.dart`），都是短值密集、长值稀疏
的手工变长编码：长度 3..10 各占一个码字（额外位 0），而 227..258 挤在
一个码字里（额外位 5）。

最大距离 32768 正好是 32KB 滑动窗口的大小 —— 这不是巧合，两者互相定义。

复制时**源和目标可以重叠**，而且必须逐字节向前复制：距离 1、长度 100
的意思是「把上一个字节重复 100 次」。用 `memcpy` 语义（先整块读再整块
写）会解错，这是移植时的经典坑。

### 同一个文件里两种位序

这是写 PNG 解码器最容易搞混的地方：

| 数据 | 位序 |
|---|---|
| Huffman 码字 | **MSB first**（从码字高位开始逐位比较） |
| 长度/距离的额外位、HLIT/HDIST/HCLEN | **LSB first** |
| PNG 的 1/2/4 位像素采样 | **MSB first** |

deflate 的位流整体是 LSB first（先取字节的低位），但 Huffman 码字在这个
流里是按 MSB first 打包的。两者并存不是设计失误 —— Huffman 码字需要
「逐位加深」的前缀匹配，而定长字段用 LSB first 更直观。

## 五种滤波器：不压缩，只是把数据变得好压

每行开头一个字节，指明本行用了哪种滤波器。

一行像素 `100 102 104 106 108` 是五个各不相同的字节，deflate 找不到重复。
每个字节减去左邻居后变成 `100 2 2 2 2` —— 一串重复的 2，deflate 一下就
吃掉了。

**滤波器一个字节都不省**，输出长度和输入完全一样。它只是把「数值相近」
改写成「数值重复」，让后面的 deflate 有东西可压。PNG 的压缩率能因它翻倍。

| 值 | 名称 | 预测值 |
|---|---|---|
| 0 | None | 0（原样） |
| 1 | Sub | 左邻 a |
| 2 | Up | 上邻 b |
| 3 | Average | `(a + b) / 2`，向下取整 |
| 4 | Paeth | a、b、c 中离 `a + b - c` 最近的那个 |

`c` 是左上角。解码时 `row[i] += 预测值`，然后 `& 0xFF`。

### 越界的邻居一律当 0

第一行没有上邻居，但规范**没有**为它定义专门的滤波器 —— 而是规定越界的
邻居当 0。于是第一行用 Up 就等于什么都不做，用 Paeth 就退化成 Sub。
编码器可以放心地对任意行选任意滤波器，解码器也不必为第一行写分支。

同理每行最左边的像素其左邻居也当 0。这条约定让五个滤波器的实现都不需要
边界判断，只需要把 prev 传 null、把 `i < bpp` 的部分单独处理。

### Paeth：三个邻居里挑一个，不求平均

```dart
int paethPredictor(int a, int b, int c) {
  final int p = a + b - c;               // 把三点当平面线性外推
  final int pa = (p - a).abs();
  final int pb = (p - b).abs();
  final int pc = (p - c).abs();
  if (pa <= pb && pa <= pc) return a;
  return pb <= pc ? b : c;
}
```

注意它返回的是三者之一，**不是算出来的 p**。这个设计很妙：在边缘处平均
值会跨过边界把两侧混在一起，而「挑最近的一个」会自动选中边缘同一侧的
邻居 —— 于是它在平坦区域表现和 Average 相当，在边缘处明显更好。

**平局时按 a、b、c 的顺序取先者**，这个顺序是规范强制的：编码器和解码器
必须在平局时做出同样的选择，否则解出来就是错的。

### Average 的和会超过 255

`a + b` 最大 510。Dart 里不会溢出，但用 C 写 PNG 时如果拿 `uint8` 存这个
和就会翻车 —— 这是移植时的经典坑，值得记一笔。

### 反滤波是串行的

第 n 行要用**已还原的**第 n-1 行做参考。所以不能并行处理，也不能跳着解。
这是 PNG 无法随机访问某一行的根本原因，也是它不适合超大图（几万像素宽）
的原因。

编码器怎么选滤波器？libpng 的启发式是逐行试全部五种，取「字节按有符号
解释后绝对值之和」最小的那个。`tool/gen_samples.dart` 也用这个办法，
于是生成出来的样图自然会混用多种滤波器，能测到「Paeth 行紧跟在 Sub 行
后面」这类手写单测碰不到的接缝。

## Adam7 隔行：七遍从模糊到清晰

1996 年的调制解调器下一张 50KB 的图要十几秒。隔行让浏览器收到 1/64 的
数据就能显示一张模糊的全图，随数据到达逐步变清晰。

把图像划成 8×8 的格子，每个位置按下表编号，第 n 遍取走所有标 n 的位置：

```
1 6 4 6 2 6 4 6
7 7 7 7 7 7 7 7
5 6 5 6 5 6 5 6
7 7 7 7 7 7 7 7
3 6 4 6 3 6 4 6
7 7 7 7 7 7 7 7
5 6 5 6 5 6 5 6
7 7 7 7 7 7 7 7
```

| 遍 | x 偏移 | y 偏移 | x 步长 | y 步长 | 像素占比 |
|---|---|---|---|---|---|
| 1 | 0 | 0 | 8 | 8 | 1/64 |
| 2 | 4 | 0 | 8 | 8 | 1/64 |
| 3 | 0 | 4 | 4 | 8 | 2/64 |
| 4 | 2 | 0 | 4 | 4 | 4/64 |
| 5 | 0 | 2 | 2 | 4 | 8/64 |
| 6 | 1 | 0 | 2 | 2 | 16/64 |
| 7 | 0 | 1 | 1 | 2 | 32/64 |

每一遍的数据量大致是之前所有遍的总和，所以清晰度提升的观感是均匀的。
最后一遍（全部奇数行）就占了一半数据。名字来自 Adam M. Costello。

### 两个必踩的坑

**1. 每遍要按本遍宽度重算行字节数。**

8×8 的 RGB8 图整行 24 字节，但第 1 遍只有 1 个像素宽，那一行是 **3**
字节。沿用 24 会让滤波和拼接同时错位，症状是图像出现斜向撕裂 —— 而且
小图上未必看得出来，正好躲过草率的测试。

**2. 宽或高为 0 的 pass 一个字节都不占。**

连滤波器类型字节都没有。小图（比如 1×1）会有好几个空 pass，漏掉这个判断
就会把后面的数据全部读偏。

### 隔行图的解压数据反而更大

每遍独立按行填充到字节边界，于是填充总量比非隔行多。本项目的
`rings_64x64_adam7.png` 样图：

```
非隔行会是  64 × (64×3 + 1) = 12352 字节
Adam7 实际              12408 字节   ← 多 56 字节
```

多出的 56 字节全部是七遍各自的行首滤波器字节与行尾填充。加上跨 pass 的
相关性被切断，隔行图的压缩率通常还要低 5% 左右 —— 宽带普及后这个功能
基本没人用了。但规范里它是**关键**特性，不支持就不能声称支持 PNG。

本项目把非隔行图也表示成「偏移 0、步长 1 的单遍」（`kSinglePass`），
于是解码主循环不必为隔行与否分叉。

## 位深缩放与 tRNS

### 缩放不是右移

4 位深的 15 要变成 8 位的 255。右移是反的（要左移），左移 4 位得到 240
—— 最白的白变成了浅灰。正确做法是按比例缩放 `v * 255 / maxValue`。

| 位深 | 算式 | 说明 |
|---|---|---|
| 1 | `v * 255` | 精确 |
| 2 | `v * 85` | 255 / 3，精确 |
| 4 | `v * 17` | 255 / 15，精确 |
| 8 | `v` | 直通 |
| 16 | `(v * 255 + 32767) ~/ 65535` | 四舍五入 |

1/2/4 位深时 255 恰好能被 maxValue 整除，所以是精确的整数乘法 ——
等价于「把该位深的位模式重复填满 8 位」。只有 16→8 需要真正的除法。

16→8 的四舍五入是可验证的：`ramp_64x64_gray16.png` 样图在 (8,0) 处
解出 0、(9,0) 处解出 1。若实现是「取高字节」而不是按比例四舍五入，
这两个点会得到不同的值 —— 测试就是这么钉住它的。

**调色板索引是唯一不该缩放的采样。** 它是编号不是亮度，缩放了就会查到
完全无关的颜色。

### tRNS 是同一个 chunk 名下的三种格式

内容取决于色彩类型，这是 PNG 里最容易读错的一块：

| 类型 | tRNS 长度 | 含义 |
|---|---|---|
| 3（调色板） | N 字节 | 第 i 个字节是第 i 号调色板项的 alpha |
| 0（灰度） | 2 字节 | 一个 16 位灰度值，等于它的像素全透明 |
| 2（RGB） | 6 字节 | 三个 16 位值，完全等于它的像素全透明 |
| 4 / 6 | —— | 禁止出现，已经有 alpha 通道了 |

后两种是「关键色」式透明：**整个颜色**被判为透明，而不是逐像素带 alpha。
GIF 的透明就是这个思路，PNG 保留它是为了让从 GIF 转过来的图不必升级成
带 alpha 通道的类型 6（那会让文件大一截）。

关键色比较有个坑：必须拿**原始位深下的采样值**去比，不能先缩放到 8 位
再比。16 位图里 `0x1234` 和 `0x1256` 缩放后都是 `0x12`，先缩放就会把不该
透明的像素也判成透明。

调色板的 tRNS **允许比调色板短** —— 未覆盖的项保持不透明。这让「只有前
几项需要透明」的常见情况不必写满 256 字节。反过来长于调色板则是错误。

## 顺序约束

PNG 的 chunk 大体可以任意排，但有几条硬性顺序，都有实际理由：

| 约束 | 理由 |
|---|---|
| `IHDR` 必须第一个 | 不然解码器连宽高都不知道，无从判断后面的数据 |
| `IEND` 必须最后一个 | 缺了它说明文件被截断 |
| `PLTE` 在 `IDAT` 之前 | 展开像素时要查表 |
| `tRNS` 在 `PLTE` 之后 | 它的 alpha 按调色板下标排，没读到 PLTE 无从对应 |
| `IDAT` 必须连续 | 见下 |

`IDAT` 的连续性最值得说。一张图的压缩数据本来是一条连续的 zlib 流，
规范却允许把它切成多个 chunk —— 这样**编码器可以流式输出**：压一点写
一点，不必先在内存里攒出完整的压缩流再回填长度。

于是解码方必须先把所有 `IDAT` 首尾相接，再当成一条流去解压。
**一个 deflate 块完全可以跨过两个 `IDAT` 的边界**，按 chunk 分别解压
必然失败。

中间插了别的 chunk 又出现 `IDAT` 则是错误。若不检查就会把两段本不相邻
的压缩数据接在一起，得到一堆无意义的字节。

## 解压炸弹与精确上限

几百字节的 deflate 流可以膨胀成几个 GB（全零数据压缩比能到 1000:1
以上）。通用解压器只能设一个宽松的兜底上限（本项目是 256MB）。

PNG 的运气好得多：`IHDR` 已经把解压后的确切字节数告诉我们了。于是
inflate 的上限设成**精确值**：

```dart
final int expected = expectedRawSize(header);
final InflateResult inflated = inflateZlib(
  file.concatIdat(),
  sizeHint: expected,   // 一次分配到位，不用扩容
  sizeLimit: expected,  // 多一个字节就报错
  format: 'PNG',
);
```

声称 1×1 的图无论压缩流里藏了多少数据，都会在第 `rawSize + 1` 个字节上
失败 —— 而且报的是「解压炸弹」而不是「数据量不符」，因为检查发生在写入
之前而不是解压完之后。

解压完成后再比一次长度：少了就说明数据被截断，这时报的是「按 IHDR
应得 N 字节，实际 M 字节」，附带宽高与色彩类型，便于判断是哪个环节算错。

## 字节级实例

一张 2×2 的 RGB8 PNG，共 82 字节。左上蓝、右上白、左下红、右下绿 ——
和 `bmp.md` 里那张例图内容完全相同，方便对照两种格式的差异。

这里刻意用 stored 块（BTYPE=00），所以像素字节在转储里肉眼可读。真实
文件当然是压缩的。

```
偏移  字节                          含义
0000  89 50 4E 47 0D 0A 1A 0A       签名
                                    —— IHDR ——
0008  00 00 00 0D                   长度 = 13
000C  49 48 44 52                   'IHDR'
0010  00 00 00 02                   宽 = 2
0014  00 00 00 02                   高 = 2
0018  08                            位深 = 8
0019  02                            色彩类型 = 2（真彩色 RGB）
001A  00                            压缩方法 = 0（deflate）
001B  00                            滤波方法 = 0
001C  00                            隔行 = 0
001D  FD D4 9A 73                   CRC-32（覆盖 'IHDR' + 13 字节数据）
                                    —— IDAT ——
0021  00 00 00 19                   长度 = 25
0025  49 44 41 54                   'IDAT'
0029  78 01                         zlib：CM=8，CINFO=7，(0x7801 % 31 == 0)
002B  01                            块头：BFINAL=1，BTYPE=00（stored）
002C  0E 00                         LEN = 14（小端）
002E  F1 FF                         NLEN = LEN 取反
0030  00                            第 0 行的 filter = None
0031  00 00 FF  FF FF FF            蓝、白（RGB 顺序）
0037  00                            第 1 行的 filter = None
0038  FF 00 00  00 FF 00            红、绿
003E  2D E0 05 FB                   Adler-32（大端，覆盖上面 14 字节）
0042  1C 47 EB B5                   CRC-32（覆盖 'IDAT' + 25 字节数据）
                                    —— IEND ——
0046  00 00 00 00                   长度 = 0
004A  49 45 4E 44                   'IEND'
004E  AE 42 60 82                   CRC-32，恒为这个值（数据为空）
```

和 BMP 那张同内容的例图对比，四处差异一起看才有意思：

* **像素顺序是 RGB**，不是 BMP 的 BGR。`00 00 FF` 在这里是蓝
* **行首多一个 filter 字节**，一行是 1 + 6 = 7 字节
* **行尾不填充**。BMP 那边 6 字节要补到 8，PNG 不补
* **第一行就是图像第一行**。BMP 默认自底向上，PNG 永远自顶向下

这 82 个字节被 `test/codecs/png_test.dart` 的「文档里那张 2×2 的例图」
一组钉住了：四个角的颜色、总长 82、解压后 14 字节、`stored×1`，以及
「改动任意一个字节都会被两道校验之一抓住」。所以这段转储不会悄悄和
代码脱节。

## 不在范围内

* **APNG 动画**（`acTL` / `fcTL` / `fdAT`）—— 是辅助 chunk，会被跳过，
  所以 APNG 能按静态图正常打开（显示第一帧）。列在阶段 2 的可选项里
* **`iCCP` 内嵌 ICC 配置文件** —— 记录在信息面板，一律按 sRGB 显示
* **`gAMA` 参与显示** —— 读出来显示，但不做 gamma 校正
* **`iTXt` / `zTXt`** —— 前者是 UTF-8 且可压缩，后者是 deflate 压缩的
  `tEXt`。都只记类型名，不解析内容
* **`sPLT` 建议调色板** —— 真彩色图里的 `PLTE` 同理，只在信息面板提一句
* **16 位输出** —— 一律降到 8 位。`RgbaImage` 是 RGBA8888，这是全项目
  统一的输出格式
